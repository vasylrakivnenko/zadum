## The top open item: the product asks one question

Five live runs, three archetypes, one to two cards each — against Rule 7's budget of **twelve**.

| scenario | archetype | decisions | cards | defaulted | judge |
|---|---|---|---|---|---|
| excel-financials | internal-dashboard | 40 | 2 | 38 | — |
| excel-financials (repeat) | internal-dashboard | 36 | **1** | 35 | 5/10 `needs_work` |
| excel-financials + `contrarianSampling` | internal-dashboard | 31 | **1** | 30 | 3/10 `not_acceptable` |
| salon-booking | booking | 50 | **1** | 49 | 5/10 `needs_work` |
| invoicing-firm | b2b-invoicing | 58 | **1** | 57 | — |

It is not the input — `salon-booking` is concrete ("booking system for my hair salon so clients can book
online instead of calling"). It is not the archetype — three behave identically. It is not a thin catalog —
`invoicing-firm` planned 58 decisions and asked one. And in **two of the five the single question asked was
not one of the four things the owner cared about**, so the owner's intent reached the spec not at all.

The stop event records what it walked away from:

    {"reason":"converged","cards":2,"settledness":0.807,
     "top_remaining":[{"node":"x5","value":20.605},{"node":"x8","value":17.845},{"node":"x7","value":16.632}]}

θ is 24. That is a question worth **86% of the threshold** abandoned, and `x5`/`x7`/`x8` are *bespoke* nodes —
the ones planned for THIS app specifically. In the real human session `x5` was asked and answered.

**Why this matters more than anything else in the session.** "Ask only what cannot be safely defaulted" is
sound only if the defaults are safe. Here 30-57 decisions per run were defaulted from a one-line description,
and an independent Opus reading the spec cold returned `needs_work, 5/10` with five concrete contradictions
and six things "a builder would still have to ask" — several of which map onto decisions never put to the
owner. A requirements engineer that asks one question is not being efficient. It is guessing.

**What was tried and did not work** (recorded so nobody repeats it):
- `contrarianSampling`, built for exactly this blind spot, changed nothing — still one card, and the spec
  scored *worse* (judge 3/10 vs 5/10).
- `relativeStopFloor` is structurally inert below two cards, so it cannot touch the worst case. Its candidate
  value 0.5 *would* have held the two-card session open (mean(46.25, 34.29) × 0.5 = 20.14 against a next
  question worth 20.605) — one live data point, recorded.
- `theta_replay` says "1.0 cards at θ=0", which reads as "θ is innocent" and is an artifact: replay can only
  stop earlier than the logged run, never ask a card that was never shown.

**No default was changed.** θ is calibrated by the harness, never by argument (CLAUDE.md), and five scenarios
are not a calibration. See ADR-041 and `docs/STATUS.md` → N1.

## Six defects the real data found

1. **The labeller re-sent the artifact digest uncached on all 5-6 feature batches**, and the prompt put the
   varying feature list *before* the constant artifact so no prefix could ever cache. Reordered +
   `cache_control`: **74% hit rate, prompt cost −63%, $0.75/repo measured.**

2. **The product could not use the best model on the account.** `llmFromEnv` had no `foundry-anthropic`
   branch, so with `AZURE_API_KEY` set the drafter/critic/compiler ran on gpt-4.1 while the *offline mining
   tools* ran on Opus 4.8. Exactly backwards. → `ZADUM_MODEL`.

3. **Compile died on Opus.** `critic` at `maxTokens: 6000` returned `Unterminated string in JSON at position
   350`. Cause: **adaptive thinking is drawn from the same `max_tokens` allowance as the answer**, so budgets
   tuned on a non-thinking model truncate mid-JSON. The first fix raised only `effort: "high"` functions and
   the next run died on `planner` (`effort: "medium"`) — so budgets are now set by **output size**, not effort,
   and a truncated response says so instead of looking like a grammar bug. ADR-042.

4. **`condense.ts` cannot tell an application from documentation about one.** `shopware/docs` yields all
   fourteen witness loci — including `db_schema`, `routes`, `payment_code` — because classification is by file
   path and a docs repo has `docs/.../payment/*.md`. Labelling one produces a true quote making a false claim,
   undetectable downstream. → `documentationHeuristic`: docs repos are 79-100% prose, real apps 14-42%,
   nothing between 55-76%.

5. **A new mechanical check, from what the judge found.** `lifecycle_state_not_in_enum` (**high**) — a
   lifecycle state with no home in the entity's persisted status enum. **4 real findings across 2 independent
   specs, 0 false positives on the other 37.** Both of the second spec's findings had been reported
   independently by the judge. Two silent failures worth remembering: the first version scored **0 on a
   known-bad spec** because it stripped `(parentheticals)` but not the compiler's `⟨src: …⟩` markers, and the
   compiler emits **two** enum syntaxes (`enum(a, b)` and `Enum: a, b`) because the section writer is an LLM.
   ADR-043.

6. **Four measurement bugs, all mine, all in the same direction.** The price table carried the pre-Opus-4.6
   rate ($15/$75 vs $5/$25) so every budget was **3× pessimistic**; output-tokens-per-call was an assumed
   2,000 against a measured **5,035**; `CHARS_PER_TOKEN` was 4 (the prose rule of thumb) against a measured
   **2.03** for code digests, so `--max-digest-tokens 20000` was silently shipping ~40k real tokens; and
   `estimateCost` was cache-blind, under-reporting the bill. Prices are now asserted in exactly one test, and
   every nominal cap was re-based so the *character* budget is unchanged.

## The graph, and why it is almost empty

All **150** small repos labelled live by Opus 4.8 → decision matrix → element statistics → design graph →
`graph:validate` clean:

    150 rows · 8 archetypes · 20,250 cells · 18,326 observable · 1,716 observed · 93 conflicts
    fill rate 9.4% · 1,359 element statistics · 6 batch errors (surfaced, not swallowed)
    → 0 soft edges · 1,401 pairs held as insufficient/low support · 0 hard proposals

**Zero soft edges is the correct answer, and getting there found a real defect in my own code.**

The first build reported *two* edges at production thresholds, the headline one being
`identity_provider=magic_link → invite_flow=invite_by_admin` with lift 4.70 and `eligible_n = 46`. It rests on
**n11 = 1, n10 = 0**. One row.

`p(B|A) = smoothed(n11, n11 + n10)` has a denominator of **1**, but `softMinN = 30` was checked against
`eligible_n` — the count of rows where both nodes were merely *observed*, which is a much larger and much
weaker quantity. The Wilson interval `[0.207, 1.000]` was the honest signal, an interval spanning 79 points,
and it still excluded the baseline 0.160, so the distinguishability test passed too. An association asserted
from a single observation, wearing a confident-looking lift, through the gate designed to stop exactly that.

`classifyPair` now applies both floors to `n11 + n10` as well, and the edge correctly reads:

    unknown — insufficient evidence: the antecedent holds in only 1 row(s) (< 10)

Three regression tests pin it, including one asserting that a well-supported edge still passes. This is the
most valuable thing the session found, and it was found only by looking at *why* a plausible-looking number
was plausible.

Two structural facts the first real matrix surfaced, both deliberately *not* acted on:
- **`negative_only` is 54% of unobserved cells** — licensed negatives collected and then used for nothing.
  A self-critique killed the obvious fix (see below).
- **93 conflicts on 150 rows**, led by `identity_provider`: real apps support several login methods while the
  catalog models one exclusive choice. The honest `conflict` status surfaced a catalog modelling error instead
  of silently picking a side.

## Two self-critique cycles, and what they changed

You asked for self-critique on architectural calls. Two rounds, both run through an outside model, both
changed the plan:

**Cycle 1 killed the biggest idea.** I proposed using the wasted licensed negatives: when every option but one
is eliminated, record the survivor as observed-by-elimination. The critique found the logical error — that
mechanism needs the option set to be **exhaustive and exclusive**, and the *same report* independently showed
it is neither (`identity_provider` is multi-valued in real apps). Worse, elimination onto a `none` option would
re-derive the banned "apps like this don't do X" prior per row. Abandoned.

**Cycle 2 rejected a second proposal and corrected cycle 1.** It threw out archetype pre-filtering of features
(it bakes an archetype guess into what is even observable, and "raises fill rate" is a denominator trick, not
new signal), and corrected its own earlier claim: it had called `absent` "the least trustworthy verdict class"
by conflating over-claimed absents with **licensed** ones, which are legitimately strong.

Its closing point is the one to carry forward: *"none of R1/R2/R3 make the product ask anything; they only
reshuffle internal bookkeeping."* That is the same conclusion the five scenario runs reached from the other
direction.

**One check was measured and then deliberately not built.** The judge found lifecycle actors the permissions
matrix does not grant. Before implementing: **zero instances across 39 specs**, and only 5 of those had a
parseable matrix at all. It would have been dead code over a format too variable to parse. Measuring first is
cheaper than deleting later.

suppresses a question. The ~40% saving was declined on that basis.
